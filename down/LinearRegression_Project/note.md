## 一、拿到任务时，我先做了什么

看到任务书，我的第一反应其实是"这不是很简单吗"——线性回归，`y = wx + b`，中学就学过。
但看到"**从零实现，不直接调用高层封装**"这几个字，我心里一紧：那我到底要写什么？

我没有立刻打开编辑器敲代码，而是先在纸上回答三个问题（因为任务书说报告里要写这三件事，
我就反过来想：**如果我是老师，我想看到什么**）：

1. **模型长什么样？**
   一个特征就是一条直线：`y_hat = w * x + b`。数据里 x 是"学习时长 hours"，
   y 是"成绩 score"，所以模型的意思是"成绩 = w × 学习时长 + b"。

2. **怎么衡量模型好不好？**
   用均方误差 MSE：把每条数据的"预测值和真实值差多少"平方后求平均。
   为什么用平方而不用绝对值？我当时的理解是"平方能让正负误差不抵消"，
   后来做实验才发现，**平方还意味着一件事：错得越离谱的点，权重越大**——
   这个细节在"异常值实验"里给我上了一课（见第五节）。

3. **怎么让模型变好？**
   梯度下降：看看往哪个方向调参数能让损失变小，就往那个方向走一小步，
   反复走。公式就两行：
   ```
   w := w - lr * dw
   b := b - lr * db
   ```

先把这三件事想清楚，我才开始动手。**这是我这次学到的第一个方法：
先把数学想清楚，代码只是把数学翻译一遍。** 后面好几次卡住，回头看，
都是因为某一步数学没想透，代码只是把"没想透"忠实地实现了出来。

## 二、第一步不是写模型，而是"把数据读进来"

我原本以为读数据是最无聊的一步，结果它给了我第一个教训。

我写了一个文件 `dataset.py`，用 Python 自带的 `csv` 模块读文件。
写完立刻遇到问题：**读出来的第一行是 `hours,score`，不是数字。**
原来 CSV 文件的第一行是"表头"，我一开始忘了跳过它。

于是我加了 `next(reader)`。但接着又想到：万一文件末尾有空行呢？
`float("")` 会直接报错，而且报错信息完全看不出是哪一行的问题。
所以我又加了两个防御：
- 空行直接跳过；
- 列数不对时，明确报出"第几行、期望几列、实际几列"。

**这里我学到一个习惯：读数据的时候，宁可多写几行检查，
也不要让错误在很远的地方才暴露出来。** 因为数据问题一旦流到后面，
你会在模型、损失函数、梯度里到处找 bug，最后发现是读文件少跳了一行——
这种排查是非常消耗人的。

为了让错误更容易定位，我还写了一个 `if __name__ == "__main__":` 的自测块，
直接运行 `python dataset.py` 就能打印出读到的样本数、前 5 条数据。
**能单独运行、单独验证的模块，调试起来轻松太多。**

## 三、最核心的一步：把梯度推出来

这是整个任务里我花时间最多的部分，也是收获最大的部分。

### 3.1 先"手推"一遍

我在纸上对单个样本的损失 `L = (y_hat - y)^2` 求导。用链式法则：

```
∂L/∂w = 2 * (y_hat - y) * ∂y_hat/∂w = 2 * (y_hat - y) * x
∂L/∂b = 2 * (y_hat - y) * ∂y_hat/∂b = 2 * (y_hat - y) * 1
```

对所有 n 个样本求平均，就得到：

```
∂L/∂w = (2/n) * Σ (y_hat_i - y_i) * x_i
∂L/∂b = (2/n) * Σ (y_hat_i - y_i)
```

然后我把这两个求和写成了矩阵乘法：

```python
diff = y_hat - y          # 形状 (n, 1)
dw = (2.0 / n) * (x.T @ diff)   # (1,n) @ (n,1) = (1,1)
db = (2.0 / n) * diff.sum()
```

**为什么非要写成矩阵乘法？** 因为我一开始写的是 Python 的 `for` 循环，
100 个样本、200 轮、再加上后面 SGD 要跑 6000 步……算得又慢又难看。
改成 `x.T @ diff` 之后，一行顶一个循环，而且和数学公式长得一模一样，
一眼就能对上。**这是我第一次真切感受到"向量化"的威力。**

### 3.2 我不信自己，所以写了一个"对拍"工具

手推的梯度，我凭什么相信它是对的？万一符号写反了、少乘了一个 x 呢？
如果梯度错了，梯度下降也会"跑"，只是永远跑不到对的地方——
这种 bug 最可怕，因为它不报错。

所以我做了两件互相印证的事：

**第一件：找"标准答案"对拍。**
线性回归在只有一个特征时，有闭式解（正规方程）：
```
w* = Σ(x_i - x̄)(y_i - ȳ) / Σ(x_i - x̄)²
b* = ȳ - w* * x̄
```
这是"一步到位"的精确解。我把它写进 `model.py` 的 `fit_closed_form()`，
然后设计了一个小测试：造一组完全符合 `y = 3x + 1` 的数据，看闭式解能不能把 3 和 1 找回来。
结果它精确返回 `w=3.000000, b=1.000000`。**这说明我的公式和实现都没问题，
也给了我一把后面用来"量梯度下降准不准"的尺子。**

**第二件：数值梯度检查（gradient check）。**
这个方法是我想了很久才想明白的，觉得特别巧妙，记录一下：
梯度的定义就是"损失对参数的瞬时变化率"，那我完全可以用"数值微分"来近似它：

```
∂L/∂w ≈ [L(w + eps) - L(w - eps)] / (2 * eps)
```

把参数轻轻推一点点（eps = 1e-6），看损失涨了多少，就能"量"出梯度。
如果这个"量"出来的值和我的公式算出来的值几乎一样，那公式就是对的。

实测结果：
```
梯度检查 dw: 解析=-21.4000000000, 数值=-21.4000000014, 差值=1.39e-09
梯度检查 db: 解析=-10.1000000000, 数值=-10.1000000043, 差值=4.34e-09
```

差值在 1e-9 量级，说明对上了。**这一刻我特别踏实**——
因为我知道后面不管训练结果多奇怪，至少"梯度"这个地基是稳的。

> 事后总结：**任何自己手写的数学，都应该找一个能独立验证的办法来对拍。**
> 闭式解、数值微分、和已知答案的小例子，都是很好的"对拍对象"。

## 四、训练循环，和那个"看起来没问题"的版本

有了模型和梯度，训练循环其实很直白：算预测 → 算损失 → 算梯度 → 更新参数，循环。

我把它写成一个 `gradient_descent()` 函数，一个函数同时支持三种模式：
- `batch_size = 全量` → **批量梯度下降 BGD**（每步看所有样本，方向最准，但最贵）
- `batch_size = 1` → **随机梯度下降 SGD**（每步看 1 个样本，方向很抖，但最便宜）
- `batch_size = 16` → **小批量梯度下降 MBGD**（折中，深度学习里最常用）

**关键细节 1：分批之后，梯度要"除以这一批的样本数"，而不是总样本数。**
我一开始想当然地用了总样本数 n，结果 batch=1 时梯度小得几乎不动。
想明白之后才发现：分批量之后，`loss` 是这一批的平均损失，
所以对它的梯度也必须是对这一批求平均，两者必须配套。

**关键细节 2：每个 epoch 都要重新打乱数据顺序。**
否则每轮的批量组成完全一样，SGD 会形成"固定的学习顺序偏见"。

**关键细节 3（写完才意识到的）：测试集只能"看"，不能"用"。**
我在训练函数里加了 `record_test` 参数，专门记录测试 loss 用来画曲线观察泛化，
但**测试集的数据绝不参与任何参数更新**。
这条线必须划清楚，否则评估结果就是假的。

## 五、第一个真正让我卡住的坑：数据尺度

第一次跑训练，我的 loss 曲线是这样的：
- lr = 0.1 → 几百轮后 loss 变成 `nan`
- lr = 0.01 → 慢慢下降，但很慢
- lr = 0.001 → 几乎是一条水平线

我当时的第一反应是："**我的梯度算错了？**"
但第 3.2 节的梯度检查明明是过的。于是我去算了一下数据的数量级：

- `hours` 的范围大概是 1 ~ 10
- `score` 的范围大概是 30 ~ 100

**两个特征的数量级差了 10 倍，而且截距 b 的量级是 30 多。**

然后我想起之前看过但没真正理解的一句话：
"梯度下降的稳定条件是 `lr < 2 / L`，其中 L 是 Hessian 矩阵的最大特征值。"
我把这句话和我们这个具体问题对上了：

MSE 对参数 (w, b) 的二阶导矩阵是：
```
L = (2/n) * [[Σx²,  Σx], [Σx,  n]]
```
在我们这份数据上（未标准化）：
- w 方向的曲率 ∝ `Σx²/n ≈ 32`
- b 方向的曲率 ∝ `1`

**两个方向的曲率差了 30 多倍。** 这意味着等高线是一个被拉得极细极长的椭圆（"峡谷"）。
后果就是：
- 能让长轴方向不爆炸的学习率，对短轴方向来说太小了 → 收敛极慢；
- 能让短轴方向快速收敛的学习率，长轴方向必然震荡发散。

**这就是"标准化"存在的意义。** 做了标准化之后：
```
x_std = (x - mean) / std
```
训练集特征的均值变成 0、标准差变成 1，两个方向的曲率接近了，等高线变成接近正圆，
梯度下降可以笔直地走向最低点。

我做了对比实验，结果非常有说服力：

| 学习率 | 原始尺度（未标准化） | 标准化后 |
|--------|---------------------|----------|
| 0.001  | 216.8（200 轮远未收敛） | 1945.4（也还没收敛，因为 lr 太小） |
| 0.01   | 62.8 | 26.3 |
| 0.05   | **1.0e+96（爆炸）** | 25.0 |
| 0.10   | **8.4e+200（爆炸）** | 25.0 |
| 0.30   | inf | 25.0 |
| 0.90   | nan | 25.0 |
| 1.20   | nan | **1.2e+62（也炸了）** |

**同一个学习率 0.05，原始尺度直接炸到 1e96，标准化后稳稳收敛到 25.0。**
可用的学习率范围被拓宽了几十倍。

> 讲一个必须注意的细节：标准化必须用**训练集的**均值和标准差去处理测试集。
> 如果分开算，就等于提前偷看了测试集的信息（数据泄露），评估结果会虚高。
> 我在 `standardize()` 里把 mean/std 一起返回，最后还用它们把参数"翻译"回原始空间：
> ```
> w = w_std / std
> b = b_std - w_std * mean / std
> ```
> 这样最后打印出来的模型是 `score = 6.24 * hours + 33.05` 这种能直接看懂的形式。
> 这个小推导我自己推出来的那一刻，觉得特别有成就感。

## 六、第二个坑（这个坑最有意思）：MAE 居然"走不动"

做"不同损失函数对比"这个实验时，我遇到了一个非常奇怪的现象：

**用 MAE 训练，200 轮之后模型什么也没学到，直线一直是 `y = 0`。**

梯度检查是过的，MSE 也能正常收敛，为什么 MAE 就不动？
我没有直接改代码去"让它动起来"，而是先想：**MAE 的梯度长什么样？**

```
∂MAE/∂w = (1/n) * Σ sign(y_hat_i - y_i) * x_i
```

关键就在这个 `sign()`（符号函数）上：
- MSE 的梯度是 `2*(误差)*x`，**误差越小，梯度越小**，接近最优点时会自动"刹车"；
- MAE 的梯度是 `±1 * x`，**它的大小和误差大小完全无关**，永远是 1，
  不会因为接近最优点而变小。

按理说"梯度不衰减"应该走得更快才对，为什么反而走不动？
我把具体数值代进去算了一遍，找到了真正的原因：

在我们的数据里：
- 标准化后 x 的范围是 ±1.5 左右，所以 `(1/n)Σsign·x` 的**最大可能值也就 1.5**；
- 而 b 方向的梯度 `(1/n)Σsign` 可以到 1。

更关键的是**要走的距离**：w 需要从 0 走到 16.4，b 需要从 0 走到 63.3。
按 lr = 0.02 算，每轮 w 最多走 `0.02 × 1.5 = 0.03`，
要走完 16.4 需要 **500 多轮**；而我把 epochs 设成了 200 —— **根本不够走。**

**所以不是代码错了，是我对"梯度大小"和"需要走多远"之间的关系没有量化的概念。**

想明白之后，解决方案也就清楚了：
**用小批量（mini-batch）**。因为分批之后梯度会除以批量大小，
相当于把梯度尺度放大了，MAE 就能在合理轮数内收敛了。
换成 `batch=16, lr=0.05` 之后，MAE 在 300 轮内顺利收敛。

> **这个坑教给我的东西**：
> 1. "训练不动"不一定是代码 bug，很可能是**优化难度**问题——
>    这时候该做的是分析梯度的大小和要走的距离，而不是瞎调学习率。
> 2. MAE 的梯度被 `sign()` 限制住了大小，所以它天生比 MSE 难优化。
>    书上都写"MAE 对异常值更鲁棒"，但很少有人告诉我"**代价是更难优化**"。
>    这个代价我是自己撞出来的，所以记得特别牢。

## 七、异常值实验：终于理解"平方"的分量有多重

修好了 MAE 之后，异常值实验终于跑出了我期待的结果。

我人为往训练集里塞了 4 个"坏点"：把几个只学了 3 小时的同学的成绩硬加了 45 分
（模拟"作弊"或者"数据录入错误"）。然后分别用三种损失训练：

| 损失函数 | 学到的直线 | 斜率偏离正确值 |
|---------|-----------|---------------|
| MSE | score = 6.372 × hours + 33.96 | **偏 4.20%** |
| MAE | score = 6.203 × hours + 32.27 | 偏 1.43% |
| Huber | score = 6.202 × hours + 32.48 | **偏 1.41%** |
| （对照）无异常值的正确值 | score = 6.115 × hours + 33.31 | — |

**MSE 被带偏得最多，MAE 和 Huber 几乎不受影响。** 为什么会这样？
我从梯度的角度想明白了：

- MSE 的梯度里有 `(y_hat - y)` 这个因子，也就是**误差越大，梯度越大**。
  一个偏了 45 分的异常点，它在梯度里的"话语权"是普通点的好几倍——
  因为 45 被平方之后变成了 2025，而普通点只有几十。
- MAE 的梯度是 `sign(误差)`，**再离谱的点也只有 ±1 的权重**。
  异常值"喊得再大声"，也只能投一票。

**这就是"鲁棒性（robustness）"的本质：限制单个样本对梯度的影响力。**
理解到这一层，我才算真正明白为什么任务书里要专门提"损失函数的意义"。

## 八、第三个坑：把图"画坏了"

做学习率实验时，lr = 1.2 那一组的 loss 炸到了 `1.2e+62`。
我照常画图，结果图完全没法看：**一个 1e62 的点把纵轴撑到了 1e62，
其他所有正常的曲线全被压成贴着 x 轴的一条直线，什么都看不出来。**

我当时还看到了满屏的 numpy 警告：
```
RuntimeWarning: overflow encountered in square
RuntimeWarning: invalid value encountered in subtract
```
一开始我以为是自己代码写错了，心里很慌。后来才想明白：
**这不是 bug，这恰恰是我想要观察的现象**——学习率太大导致参数指数级增长，
超出了浮点数能表示的范围。它只是"喊得太大声"，把真正的信息盖住了。

于是我做了两件事：
1. 写了一个 `clip_curve()` 函数，把超过显示上限的数值截断成 nan
   （nan 在 matplotlib 里等于"断开不画"），
   这样图上只保留"从起点往上冲"的那一小段，既能看到它发散了，又不破坏整张图。
2. 用 `np.errstate(over="ignore", invalid="ignore")` 把这类数值警告临时关掉，
   让日志清爽一点（训练结束后自动恢复，不影响别的地方）。

**这件事让我意识到：做实验时，"会发散"本身就是结果的一部分，
不应该把它藏起来，而应该想办法把它"展示得体面一点"。**

## 九、最反直觉的一次：动量居然让它变慢了

这是我这次做实验最有意思的一段经历，必须完整写下来。

我的"想当然"是：动量（Momentum）是加速收敛的技巧，加上它一定会更快。
于是我拿 lr = 0.6 做了对比实验，预期"加动量"的曲线会一骑绝尘。

**结果完全相反：加了动量之后，loss 震荡得更厉害，收敛反而更慢了。**
我第一反应是"动量写错了"，把代码反复看了好几遍：

```python
v = momentum * v + (1.0 - momentum) * dw
w = w - lr * v
```

这看起来没问题啊。于是我先不猜，而是**做了一轮参数扫描**，
把不同学习率下单用 BGD 和 BGD+动量 的"第几轮进入最优附近"列出来：

| 学习率 | 纯 BGD 达标轮数 | +动量 0.9 达标轮数 |
|--------|----------------|-------------------|
| 0.1    | 21 | 37 |
| 0.5    | 1 | 34 |
| 0.9    | 21 | 25 |
| 0.99   | 225 | 51 |
| 1.0    | **永不收敛（炸到 4302）** | **10** |
| 1.2    | 发散 | 发散 |

看到这张表，我一下就明白了：

1. **动量在这里不是"白送"的。** 在我们采用的 `v = βv + (1-β)g` 这种写法里，
   动量的"有效步长"大约等于 `lr / (1 - β)`。
   β = 0.9 时，相当于**把学习率乘了 10 倍**。
   所以在 lr = 0.6 这种本来就不小的学习率上再加动量，
   等于把步长推到 6，当然会剧烈震荡。
2. **但动量有一个不可替代的价值：在学习率接近稳定边界时"救场"。**
   看 lr = 1.0 那一行：纯 BGD 直接爆炸（loss = 4302.4），
   而加了动量之后，它居然在第 10 轮就收敛了！
3. **它更大的价值是配合学习率衰减一起用**（前期大步、后期小步）。

于是我重新设计了实验，做三个场景：温和 lr=0.1（动量帮助有限）、
临界 lr=1.0（动量救场）、衰减 lr=0.5（配合使用）。
这次的结论才既真实又完整。

**这段经历教给我的东西，比"学会用动量"重要得多：**

- **实验结果和教科书不一致时，不要急着改代码，也不要急着否定教科书。**
  先怀疑自己的实验设计——很可能是我把两个变量混在一起比较了。
- **"更好的方法"通常是有前提条件的。** 动量的前提是"学习率要相应调小"，
  或者"本来就该用个更大的学习率"。脱离前提谈好坏是没有意义的。
- **用"达标轮数"而不是"最后一轮的 loss"来评价优化器。**
  我一开始只看最后一轮的 loss（25.05 vs 24.98），
  这种差别小到可能只是随机波动，根本说明不了问题。

## 十、我是怎么组织这个项目的

代码我没有全写在一个文件里，而是按"一件事一个文件"分开：

```
LinearRegression_Project/
├── code/
│   ├── dataset.py          只负责：读 CSV、标准化、切分、提供小批量迭代器
│   ├── model.py            只负责：模型前向、损失函数、梯度、闭式解
│   └── train.py            只负责：优化算法、训练循环、跑实验、画图、存结果
├── data/
│   ├── train.csv           训练集（100 条）
│   └── test.csv            测试集（30 条）
├── results/                运行 train.py 后自动生成的全部产物
│   ├── 01_loss_curve.png ~ 10_residuals.png   10 张实验结果图
│   ├── results.json        所有关键指标的汇总（报告里的数字都从这里来）
│   ├── final_training_curve.csv    最终模型的逐轮 loss / 学习率
│   ├── test_predictions.csv        测试集逐条预测值与残差
│   └── run_log.txt         完整训练日志
├── tools/
│   └── make_report.py      读 results/ 里的数据和图，自动排版生成 report.pdf
├── report.pdf              实验报告
├── requirements.txt        环境配置
└── note.md                 这份学习笔记
```

**关于 `tools/make_report.py`（说明一下，因为它超出了任务书要求的文件清单）：**
我一开始是打算手写报告的，但写到一半发现一个问题——
报告里到处是数字（学习率、损失值、达标轮数……），只要我改一次代码重新训练，
手抄的数字就可能对不上了，而且很容易抄错。
所以我把报告也变成了"由代码生成"：
`train.py` 把所有指标存进 `results.json`，`make_report.py` 读它并自动排版。
**这样报告里的每一个数字都能追溯到某一次真实的训练，改代码重跑就能自动同步。**
它不影响任务书要求的三个核心文件，但我觉得它体现了"结果可复现"这个意识。

**为什么这样分模块？** 因为我在写的过程中真的体会到了好处：
- 改梯度公式时，我只需要动 `model.py`，完全不用担心数据读取；
- 排查"MAE 走不动"时，我写了个临时脚本 `_probe_lr.py`（验证完就删了），
  直接 `import` 这两个模块，几行代码就把不同学习率全试了一遍。
  **如果所有代码都挤在一个文件里，这种"快速试探"根本做不到。**

另外几个我刻意养成的小习惯：
- **每个文件都能单独运行**（`if __name__ == "__main__":`），
  直接跑 `python model.py` 就会做自测（梯度检查、损失函数对拍）。
- **所有结果都存成文件**：图片存 `results/*.png`，指标存 `results/results.json`，
  逐条预测存 `results/test_predictions.csv`。
  这样报告里的每个数字都能追溯到原始文件，不用凭记忆抄。
- **固定随机种子（seed = 42）**。带随机性的实验一定要固定种子，
  否则每次跑的结果都不一样，实验根本没法对比。

## 十一、目前还没解决的问题

说实话，有几个地方我到现在也没完全弄明白，我列在这里：

1. **动量"救场"的确切数学条件。**
   我观察到了 lr = 1.0 时纯 BGD 爆炸、加动量反而收敛，
   但我还没能自己推导出"加了动量之后稳定条件变成什么"。
   我只知道一个直觉解释：动量的惯性会"平滑"掉高频的来回震荡，
   但为什么它能容忍更大的学习率，我需要再推一遍。

2. **测试集和训练集的指标差距。**
   最终模型：训练集 MSE = 25.20、测试集 MSE = 20.58。
   测试集居然比训练集还好——这有点反直觉。
   我猜测原因是训练集里有几个"低时长但高分"的点拉高了训练误差，
   但我没有定量验证过这个猜测。

3. **L2 正则化在这份数据上几乎没用。**
   我实现了 L2（`l2 * w` 加到梯度里），但在这份"只有一个特征、数据量很小"的数据上，
   加不加它对结果几乎没有区别。我还不太清楚在什么规模的数据上它才会明显起作用。

4. **超参数是用训练集选的，这不够严谨。**
   我是用"训练集上的 loss 曲线"来挑学习率的。严格的做法应该是
   从训练集里再切出一份"验证集"专门调参，测试集只在最后评估一次。
   本次因为数据只有 100 条（再切就更少了），我采用了务实做法，
   并在报告里把这个局限写清楚。**我知道这不是最好的做法，只是当下权衡的结果。**

5. **没有和其他优化器对比。**
   Adam、RMSProp 这些我只听说过名字，还没自己实现过。
   我猜它们能改善"不同方向曲率差别大"的问题（也就是标准化想解决的问题），
   但这只是我的猜测。

## 十二、如果重新做一遍，我会怎么改

1. **先写"最小可运行版本"，再加功能。**
   我一开始就想着"要支持三种梯度下降 + 动量 + 衰减 + 三种损失"，
   结果前期调试时变量太多，一个实验出问题很难定位。
   更好的做法应该是：先写最朴素的 BGD + MSE，跑通了，再加别的。

2. **先做梯度检查，再开始训练。**
   这次我是写完之后才做的检查。如果一开始就做，
   后面遇到"MAE 走不动"时，我就能更快地排除"梯度写错"这个可能，
   直接去思考数学原因。

3. **给实验设计留出"对照"的意识。**
   动量那个坑的根源就是：我一次改了学习率和动量两个东西，
   却没有做"同一个学习率下的对照"。**做实验时，一次只变一个变量。**

## 十三、我这次真正学到的东西（总结）

**技术层面的：**
- 线性回归的模型、MSE 损失、梯度下降的更新公式，现在我能自己从零推出来、写出来了；
- 三种梯度下降（BGD / SGD / MBGD）的区别不只是"批量大小"，
  还牵涉到"每轮更新几次"和"梯度噪声多大"这两个不同的维度；
- **特征标准化不是可选项，而是梯度下降能不能跑起来的前提条件**，
  它的本质是让损失函数的等高线不要被拉成细长的峡谷；
- 损失函数的选择会直接决定模型对异常值的敏感程度，
  根子在"梯度里误差的权重是几次方"；
- 动量和学习率衰减都有用，但都有前提条件，不能无脑加。

**方法和习惯层面的（我觉得这些比上面的更重要）：**
- **先想数学，再写代码。** 代码是数学的翻译，数学没想清楚，代码只会忠实地错下去。
- **自己写的东西，一定要找办法对拍。** 闭式解、数值梯度、已知答案的小例子，
  都是很好的验证工具。有对拍，我才敢相信自己。
- **实验出问题时，先怀疑实验设计，再怀疑代码。** 动量那次，
  如果我一上来就改代码，可能会把正确的实现改坏。
- **一次只变一个变量。** 这是做对照实验的基本纪律。
- **把过程记录下来。** 这篇 note.md 里很多细节，
  如果我不是在做的过程中就写下来，现在肯定想不起来了——
  而恰恰是这些"当时为什么这么想"的细节，才是最值得留下的东西。

## 十四、最后

做完这个任务，我最大的感受是：
**以前我以为"线性回归很简单"，现在我知道"简单"和"真正理解"之间隔着多少东西。**

一行 `sklearn.linear_model.LinearRegression().fit(x, y)` 能算出同样的直线，
但它不会告诉你：为什么数据要标准化、为什么学习率大会发散、
为什么 MAE 更难优化、为什么动量的有效步长是 `lr/(1-β)`。

而这些"为什么"，恰好就是这个任务真正想让我学会的东西。

这个项目里的每一行代码我都写了中文注释，
**因为我知道一周后的自己会忘记"这行为什么要这么写"。**
注释不是写给老师的，是写给未来那个已经忘光了的自己的。
